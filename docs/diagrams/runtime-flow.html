How the pieces actually talk to each other

Two pictures of the same app: what runs, on which port, and who's allowed to call whom — once while you're coding it, and once after it's shipped.

1. While you're developing

Two independent server processes run on your machine at once. Your browser is the only thing that talks to both — nothing is relayed between them.

2. After it's shipped

Vite's translation happens once, ahead of time, not live per request. The output is handed to nginx, which becomes the single door the browser talks to.

3. Who does what

The same five components, read across development and production.

Component What it actually is Role in development Role in production
React source.tsx / .ts Your app's code — components, logic, JSX. Watched and live-translated on every save. Compiled once into dist/, then untouched.
Vitebuild tool Translator: TS/JSX → plain JS the browser understands. Runs a dev server on :5173, serves + hot-reloads live. Runs once (npm run build), then exits.
Spring Bootapp server Embedded Tomcat running your REST API. Runs on :8080, needs CORS to accept the :5173 origin. Runs on :8080 internally, only nginx talks to it directly.
PostgreSQLdatabase Where the app's actual data lives. Runs in Docker on :5432 — not wired up yet (Phase 1+). Managed or self-hosted, reachable only by Spring Boot.
nginxweb server The public front door for real visitors. Not running — no role yet, nothing to route. Serves dist/ directly, reverse-proxies /api/*.
The one thing that flips: in development the browser is a client of two separate origins (hence CORS). In production it's a client of one — nginx — which quietly does the routing that CORS used to do explicitly.
